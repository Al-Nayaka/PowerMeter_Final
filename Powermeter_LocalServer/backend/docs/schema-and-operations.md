# Schema and local operations

## Baseline and approval boundary

The full Backend PRD v1.0 dated 9 November 2026 describes a pre-existing schema but no authoritative SQL schema was supplied. `migrations/001_core.sql` is therefore an **explicit proposed baseline for a fresh PostgreSQL database**, not an assertion of compatibility with any installed database. Storage names follow the PRD and implemented repositories exactly: `devices.device_name` and `devices.is_enabled`. All timestamps use `TIMESTAMPTZ`, including `recorded_at`; ISO timestamps must include a timezone.

Baseline tables: `devices`, `measurements`, `relay_states`, `system_events`. IDs are BIGSERIAL/BIGINT; do not cast IDs to unsafe JavaScript numbers. Topic prefix is constrained to `powermeter/` plus an ASCII alphanumeric, underscore or hyphen device code. Only relay 1 exists. Measurement values have the specified NUMERIC precision and scale; `power_factor` is nullable and constrained to [0,1]. PostgreSQL NUMERIC driver results normally remain strings. Invalid/nonfinite samples must still be rejected before inserting; database constraints provide a second boundary. Use `recorded_at DESC, id DESC` for latest/history and `changed_at DESC, id DESC` for relay state. Device deletion is restricted by measurements/relays/commands; system events alone use `ON DELETE SET NULL`.

`002_ingestion_and_commands.sql` is **separately proposed PRD section 5.6 enhancements**:

- `measurements.received_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` records server ingestion time. Backfilled old rows get migration time, not their historical arrival time.
- Nullable `message_id VARCHAR(128)`, unique `(device_id, message_id)`. Multiple NULL IDs remain permitted. QoS 1 replay with a non-null repeated ID must not insert/broadcast a second stored measurement. App repositories should use `ON CONFLICT (device_id, message_id) DO NOTHING` and check insertion result.
- `relay_commands`: UUID `command_id` generated by application, device FK, relay 1, boolean desired state, statuses `requested`, `published`, `confirmed`, `timed_out`, `failed`, requested/published/confirmed timestamps, nullable error. `acknowledged` is not a separate status: a matching device acknowledgement is `confirmed`. The illustrative PRD `cmd-000001` string is replaced by a real UUID. State transitions and matching command/device/relay/state are application responsibilities.

**Both migrations are required by the completed backend**, but neither was applied by this implementation. Authoring files is not approval to mutate a database. Review both SQL files and separately authorize 002 before executing. Baseline-only installation is a review/prototype stage, not a supported production runtime for the enhanced backend.

## Migration runner

Run from `backend/` with dependencies installed. Scripts use standalone `pg` pools, never import application `src/`, and load optional dotenv configuration without writing any environment file. Environment: `DATABASE_URL`, or `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`; libpq `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` are fallback alternatives. Use a migration-owner role for DDL and a separate least-privilege backend role for runtime. Require certificate verification for remote PostgreSQL; never disable TLS verification to work around certificate errors.

```sh
# No DB connection or mutation: lists selected local files.
node scripts/migrate.js
node scripts/migrate.js --approve-enhancements

# Operator-authorized mutation only, on the reviewed target database.
node scripts/migrate.js --apply
node scripts/migrate.js --apply --approve-enhancements
```

The runner takes a session advisory lock; each migration SQL and its tracking row commit in one transaction. `public.schema_migrations` tracks filename, SHA-256 checksum and applied time. Existing public tables without migration history are refused, not silently adopted. Missing/edited applied files or out-of-order history are refused. Keep applied files immutable; add a numbered migration for future changes. A checksum mismatch is not resolved by editing tracking rows. `--apply` without enhancement approval can verify an already-applied 002 but cannot newly apply it. There is no automatic startup migration, destructive rollback, or down command. On failure, fix the cause and retry; successful earlier migrations stay committed. Reconcile legacy schema in a separately reviewed migration/import plan or use a new database; do not drop production tables to bypass the guard.

Verification without services:

```sh
node --test scripts/*.test.js
node --check scripts/migrate.js
```

These tests validate planning, checksum drift, refusal and rollback with fake clients, plus simulator numeric output/configuration bounds. They are not live PostgreSQL or MQTT integration tests. The application's `tests/*.test.js` command does not automatically include script tests.

## Development seed and simulator

```sh
NODE_ENV=development node scripts/seed.js --apply
SIM_DEVICE_CODE=PM-ESP32-001 node scripts/simulate.js
```

On PowerShell, set environment with `$env:NODE_ENV='development'` (and similarly for other variables), then run the Node command. Seed requires explicit `NODE_ENV=development` in the parent shell and `--apply`, creates only `PM-ESP32-001..003`, uses canonical prefixes, and leaves existing records unchanged, including disabled status. It never enables or overwrites existing devices. Do not seed production.

Simulator: `MQTT_URL` (default `mqtt://127.0.0.1:1883`), `MQTT_USERNAME`, `MQTT_PASSWORD`; `SIM_DEVICE_CODE` (default `PM-ESP32-001`), `SIM_MEASUREMENT_MS` (1000), `SIM_HEARTBEAT_MS` (15000). Use the matching dedicated device MQTT account. Run a separate process for each device; do not run alongside real firmware using the same identity. It does not auto-register devices and deliberately sends only normal samples. It publishes numeric finite samples with ISO UTC timestamps, cumulative Wh and a UUID boot token plus monotonic sequence `message_id`. Restart creates a new boot token and resets simulated cumulative energy: this is a device reset, never an interval-consumption sum. Graceful stop publishes retained offline; broker LWT handles abrupt loss. Retained commands are ignored.

## Manual retention

Default proposal: retain raw measurements for 30 days; operator must evaluate storage/load and approve policy. No cron/timer or automatic schedule is installed.

```sh
node scripts/retention.js
node scripts/retention.js --apply
```

Dry-run is default; it queries a capped candidate sample but never deletes. `RETENTION_DAYS=30`, `RETENTION_BATCH_SIZE=1000` (max 10000), `RETENTION_MAX_BATCHES=10` (max 1000) bound the work per invocation. Each applied batch is one committed SQL statement using `FOR UPDATE SKIP LOCKED`. Only `measurements.recorded_at` determines age; devices, events, relay states, commands and migration history are untouched. No full-table count, cascade, truncate, vacuum full or rollback deletion is performed. Dry-run sample is capped at batch × max batches + 1, not an exact total. Application inserts may continue, so results are not a snapshot across invocations. At scale, evaluate an age index/partitioning as another approved migration; current per-device indexes do not optimize a global age sweep. Back up first, monitor execution time/WAL/disk, and repeat manually only as needed. Deletion is irreversible except through a tested backup restore.
